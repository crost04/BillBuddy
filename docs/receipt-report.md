# Receipt scan – evaluation report

Generated by `python -m billbuddy.ml.receipt_ocr.evaluate` on 2026-10-31: 400 synthetic receipts per noise level (random seed 42).

## 1. Data understanding and preparation

No real receipts are available yet (cold start). `synthetic.py` generates receipts in the layouts of German shop types (Rewe/Edeka style, Lidl/Rossmann style, Aldi/Penny style, dm style, bakery) with quantity lines ("2 Stk x 0,59"), deposit, discounts, cash payment with change, VAT lines and two date formats. The dm style prints the tax rate as a digit behind the price ("2,45 1"), the quantity in front of the name ("3x 0,85 Fruchtgummi") and a subtotal with a discount below it. `ocr_noise` then simulates typical text-recognition mistakes: confused characters (0↔O, 1↔l, 5↔S, ","→"."), look-alike digits (3↔2, 5↔9, 6↔8 – seen on real receipts, no rule can repair them), missing or extra spaces and lost lines. Noise level = probability per character.

Example (noise 5 %):

```
EDEKA Schmidt
Hauptstr. 5
91054 Er1angen
JOGHURT NAT UR             2,88 A
   3 Stk x 0,96
GOUDA JUNG              2,87 A
BRÖTCHEN                0,34 A
HAFERFLOCKEN             3,69 A
   3Stk x 1,23
VOLLMILCH 3,5%            1,34 B

  2 Stk x 0,33
--------------------------
S UMME           EUR l1,78
```

## 3. Iteration: what the first evaluation changed

The first parser version broke down with noise: OCR split "SUMME" into "S UMME" or turned it into "SUMMC", so the total line was not found, and dates like "28.1O.2O26" were not repaired. Improvements: keywords are compared without spaces and with one wrong letter allowed; date-shaped text gets the same digit repair as amounts; shop names are compared with confusable characters unified. (Both columns measured with the noise model of the first evaluation, without look-alike digits.)

| Noise | Total – first version | Total – now | Date – first version | Date – now |
|---|---|---|---|---|
| 1.0 % | 94.5 % | 99.5 % | 98.2 % | 98.5 % |
| 3.0 % | 84.8 % | 99.0 % | 91.5 % | 92.2 % |
| 5.0 % | 79.0 % | 97.5 % | 83.0 % | 85.8 % |
| 10.0 % | 62.5 % | 93.5 % | 69.8 % | 75.0 % |

## 5. Built-in plausibility check

If the items add up to the total, the scan is very likely complete. Share of receipts where this check passed **and** the total was right:

| Noise | Check passed | Check passed and total right |
|---|---|---|
| 0.0 % | 100.0 % | 100.0 % |
| 1.0 % | 93.5 % | 93.5 % |
| 3.0 % | 70.0 % | 70.0 % |
| 5.0 % | 61.8 % | 61.8 % |
| 10.0 % | 34.5 % | 34.0 % |

When the check passes, the total is practically always right – so the app can tell the user whether to double-check the scan.

## 6. Several readings and the exact-sum repair

The phone reads every photo several times; the server takes the items of the most plausible reading and may then replace or add up to two items with what another reading saw in the same line – but only if the items then add up to the total to the cent (`combine.py`). Here every receipt is read 3 times with independent noise. "Complete" = the items add up to the right total; "complete but wrong" = they add up, yet are not the receipt's items (the risk of the repair).

| Noise | Items F1: best reading | Items F1: with repair | Complete: best reading | Complete: with repair | Complete but wrong: best / with repair |
|---|---|---|---|---|---|
| 3.0 % | 99.8 % | 99.9 % | 98.2 % | 99.5 % | 0.2 % / 0.2 % |
| 5.0 % | 98.8 % | 99.7 % | 92.0 % | 98.2 % | 0.5 % / 0.5 % |
| 10.0 % | 95.1 % | 97.7 % | 71.5 % | 90.8 % | 1.2 % / 1.5 % |

The repair turns many incomplete scans into complete ones, while the share of wrong scans that pass the check barely rises: the exact sum to the cent is a strict test that a wrong value rarely passes by chance. Independent noise is optimistic – real readings of one photo make similar mistakes – so the real gain is smaller (see docs/crisp-dm.md).

## 7. Limits

- Synthetic receipts are tidier than real photos (folds, shadows, faded thermal paper, tilted shots). The real accuracy has to be measured with real receipts. Two real receipts (photographed on a table, each in 4 photo variants) are evaluated in docs/crisp-dm.md: a discounter receipt with 28 item lines (26.75 of 28 items found, complete in 2 of 4 variants) and a drugstore receipt with 5 item lines (complete in all 4 variants); total, date and store were right in every variant.
- Item names are kept as recognized; the evaluation matches items by amount.
